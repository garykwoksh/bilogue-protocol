# 點解 Agent 需要一個 Consent Layer？

> 設計文章 — 解釋 Bilogue Protocol 背後嘅問題意識同設計抉擇。
> 目標讀者：用緊 AI agent 做自動化嘅開發者、技術負責人。

## 1. 問題：Agent 已經識做嘢，但冇人睇住佢

2024–2026 年，agent 由 demo 變成生產力工具：自動回 email、自動落單、自動改 code、自動過數。能力越大，單次失誤嘅代價越大。

現實已經出現過嘅事故類型：

- **失控執行**：agent 喺冇人批准下提交程式碼、發出付款，造成實質金錢損失（公開報道過單次事故損失達數萬美元級別）。
- **權限錯配**：一個換咗模型、換咗 API key 嘅 agent，系統照舊當佢係「自己人」，因為傳統 ACL 認嘅係 credential，唔係身份。
- **死無對證**：出事之後，冇一份完整、可信嘅 log 話你知「邊個 agent、幾時、做咗咩、經邊個批准」。

結論：**問題唔係 agent 唔夠叻，而係冇一個標準化嘅「人類把關位」。**

## 2. 點解現有標準補唔到呢個位？

| 標準 | 解決咗咩 | 冇解決咩 |
|---|---|---|
| **MCP**（Anthropic） | agent 點樣標準化咁用工具 | 冇規定用工具之前要有人批准 |
| **A2A**（Google） | agent 之間點樣傳訊息、委派任務 | 傳訊息本身唔等於授權執行；冇 consent 語義 |
| 各家 agent 框架 | 各自有啲 approval callback | 每間做法唔同，冇互通、冇標準 audit 格式 |

即係話：而家個生態有「手腳」（MCP）、有「嘴」（A2A），但冇「韁繩」。Bilogue 嘅定位就係做條韁繩——而且係一條可以疊喺任何現有標準上面嘅韁繩，唔使你拆咗現有架構。

## 3. 設計抉擇

### 3.1 認 ID，唔認模型

> **模型係引擎，Agent ID 係電話號碼。**

ACL 綁定嘅係 Agent ID＋HMAC 簽名，唔係背後用緊邊個模型。今日用 GPT，明日轉 Claude，個「人」仲係同一個人，權限唔使重新申請。呢個亦都係點解換 model 唔應該等於換身份。

### 3.2 三級 Consent，唔係得個「撳掣」

一刀切嘅 per-message approval 喺生產環境會煩死人。所以 Bilogue 分三級：

- **L1**：每條訊息都要人批——最嚴，用喺高風險動作（過數、刪 data）。
- **L2**：對話級授權（TTL）——批咗一段對話，雙向自動放行，適合協作流程。
- **L3**：預算上限授權——「呢個月最多用 $X」，適合可量化風險嘅自動化。

原則：**風險越高，批准越貼近每次執行；風險越低，授權越批量。**

### 3.3 Kill-switch 係一等公民

`stop` 唔係「優雅關機」，係 kill-switch。任何人類操作員喺任何時候都可以即刻斷咗成條 agent 鏈。呢個係設計入面寫死嘅，唔係事後加嘅 admin 功能。

### 3.4 Audit log 係 append-only

所有 consent 決定、所有訊息收發，全部寫入 append-only JSONL log。唔係為咗 compliance 而做樣，而係因為：**冇 log 嘅批准，喺出事嗰陣等於冇批准過。**

## 4. 唔係要取代邊個

重申一次定位，避免誤會：

- 你繼續用 MCP 接工具，繼續用 A2A 做 agent 互通——Bilogue 唔係嚟搶呢啲位。
- Bilogue 係一個**治理層**：當你嘅 agent 準備做有副作用嘅事之前，佢問一句「真係做？」
- 參考實作只係 3,400 行 Python，任何框架都可以照住 SPEC 自己實作，或者直接用個 relay。

## 5. 未解決嘅問題（老實講）

- 項目只經過作者三輪自審，**未經獨立第三方安全審計**，唔好直接用喺生產環境處理真錢。
- Consent UX（點樣批得快又唔批錯）係一個產品問題，protocol 只定義語義，唔包 UI。
- 大規模部署下嘅批准疲勞（approval fatigue）需要實際數據先知點調 L1/L2/L3 嘅比例。
